# Composite Foreign Key Support — Execution Plan

Goal: support composite (multi-column) foreign keys end-to-end, e.g.

```xml
<unique>
  <column name="ID"/>
  <column name="PropertyID"/>
</unique>
...
<relations>
  <compositeRelation table="Assignment" type="cascade">
    <column src="ParentAssignmentID" name="ID"/>
    <column src="PropertyID" name="PropertyID"/>
  </compositeRelation>
</relations>
```

generating (Postgres example):

```sql
foreign key (ParentAssignmentID, PropertyID) references Assignment (ID, PropertyID)
```

**Design decisions (locked in):**
- XML: a new sibling element `<compositeRelation table="..." type="...">` inside `<relations>`, holding two-or-more nested `<column src="..." name="..."/>` children (each pairs one local column with the target-table column it maps to). The existing `<relation src=... table=... column=... type=.../>` single-column element is completely unchanged — `<relations>` is now a `<choice>` between the two element names. This was chosen over overloading `<relation>` with optional attributes *and* an optional nested-column sequence: that approach required the parser to reject the "both forms present" / "neither form present" states by hand, whereas a separate element makes those states structurally unrepresentable in the XSD itself (confirmed via `xmllint --schema`: a `compositeRelation` with only one `<column>` child is rejected by the XSD directly, no parser guard needed).
- `Relation::new(...)` (single-column constructor, used in 650+ call sites across the workspace: model/parser/generator tests, `mermaid`/`plantuml` diagram generators, `schema-migration-generator` tests, etc.) keeps its exact signature and behavior. Composite relations are constructed through a new API. This means most of the codebase needs zero changes.
- Internally `Relation` (the Rust struct — there is *no* separate `CompositeRelation` Rust type, only a separate XML element) moves from a single `(from_column, to_column)` pair to a `Vec<(from_column, to_column)>`. `from_column_name()`/`to_column_name()` become "first pair" convenience accessors (used everywhere today, all still single-column call sites) backed by a new `column_pairs()` accessor.

Work is split into independently-committable chunks, each with its own build+test checkpoint. Do not start chunk N+1 until chunk N compiles and `cargo test --workspace` passes. Check off `[x]` here as chunks complete.

## Chunk 9 — `ForeignKeyMode::Triggers` composite support (formalized from backlog) [x] done (2026-09-24)

- [x] Resolution chosen: implement full composite trigger SQL (not an error), since Postgres row-level triggers made this tractable (`OLD.`/`NEW.` refer to a single row, so a composite check is just an AND-joined multi-column equality — no new SQL primitive needed) and the SQL Server set-based case, while it needed a real shape change, doesn't need a hard error either.
- [x] `schema-sql-generator/src/postgresql/postgres_trigger_generator.rs`: added an `old_match_where_clause` helper joining every `column_pairs()` pair as `{from} = OLD.{to}` with `" and "`. Delete-trigger Enforce/SetNull/Cascade bodies now use it (SetNull's `set` clause also lists every from-column). Update-trigger validation now ANDs a `new.{col} is not null` guard per column pair (MATCH SIMPLE semantics: skip the check unless *all* referencing columns are non-null) before ANDing a `{to} = new.{from}` match per pair, and the error message lists all from-columns comma-joined. Single-column behavior is produced by the same code path (a 1-pair `column_pairs()` list) and is byte-identical to the pre-change output — verified by the untouched pre-existing tests passing unmodified.
- [x] `schema-sql-generator/src/sqlserver/sqlserver_trigger_generator.rs`: SQL Server's `in (select col from deleted/inserted)` single-column idiom has no direct multi-column equivalent, so composite relations branch (`relation.is_composite()`) onto a join-based shape instead, while the single-column branch is the original code verbatim (confirmed byte-identical via the untouched pre-existing tests): Enforce delete uses `if exists (select 1 from child c inner join deleted d on c.col1 = d.pcol1 and ...)` (message simplified to a static string for composite - the old dynamic "@msg with the offending value" trick doesn't generalize to a multi-column key without a lot more SQL, and a static message is an acceptable tradeoff here); SetNull/Cascade use `update ... from child inner join deleted on ...` / `delete child from child inner join deleted on ...`; the update-trigger validation uses `if exists (select 1 from inserted i where <all-not-null> and not exists (select 1 from parent p where <all-pairs-match>))`.
- [x] Regression tests added: 4 in `postgres_trigger_generator.rs` (Enforce/SetNull/Cascade delete-trigger composite where/set clauses, plus the update-trigger's all-not-null-guard + all-pairs-match + comma-joined column list in the error message), 4 in `sqlserver_trigger_generator.rs` (same four shapes, asserting the join-based SQL). All new composite fixtures needed an explicit primary key on the parent table for `should_output_delete_trigger`'s `table.primary_key().is_some()` gate - caught by two initial test failures before adding it.
